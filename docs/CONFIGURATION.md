# Canopy Configuration Reference

This document covers all configuration options for Canopy.

## Configuration Files

| File | Location | Purpose |
|------|----------|---------|
| `config.toml` | `.canopy/config.toml` | General canopy configuration |
| `sandbox.toml` | `.canopy/sandbox.toml` | Per-project sandbox settings |
| `validation.toml` | `.canopy/validation.toml` | Task validation settings |
| `repositories.json` | `~/.cache/canopy/` | Repository identity registry |
| `runs.db` | `~/.cache/canopy/` | SQLite run history |
| `daemon.log` | `~/.cache/canopy/` | Daemon log file |

---

## General Configuration

The general configuration file controls canopy behavior. Create it manually at `.canopy/config.toml`.

### Location

```
<project>/.canopy/config.toml
```

### Full Example

```toml
# Canopy Configuration
# General configuration for canopy orchestration.

[resolver]
# Timeout for resolver agents when resolving merge conflicts.
# Resolver agents are spawned when parallel agent changes conflict.
# Default: 10m (10 minutes)
# Format: Go duration string (e.g., "10m", "15m", "1h", "30m")
timeout = "15m"
```

### [resolver]

Resolver agent settings.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `timeout` | string | `"10m"` | Timeout for resolver agent operations |

Duration format: Go duration string (e.g., `"10m"`, `"15m"`, `"1h"`, `"30m"`)

### Configuration Precedence

The resolver timeout can be configured through multiple sources. The precedence order is:

1. **CLI flag** (`--resolver-timeout`): Highest priority
2. **Environment variable** (`CANOPY_RESOLVER_TIMEOUT`): Second priority
3. **Config file** (`.canopy/config.toml`): Third priority
4. **Default** (`10m`): Used if no other source is configured

Example:

```bash
# CLI flag takes precedence
canopy run --resolver-timeout 20m

# Environment variable (if no CLI flag)
CANOPY_RESOLVER_TIMEOUT=15m canopy run

# Config file (if no CLI flag or env var)
# .canopy/config.toml: [resolver] timeout = "12m"
canopy run
```

## Sandbox Configuration

The sandbox configuration file controls how agents are isolated. Generate it with `canopy init` or create manually.

### Location

```
<project>/.canopy/sandbox.toml
```

### Full Example

```toml
# Canopy Sandbox Configuration
# Generated by: canopy init
# Documentation: https://github.com/jzila/canopy/docs/CONFIGURATION.md

[sandbox]
# Enable bubblewrap sandboxing
enabled = true

# Network access policy: "allow", "deny"
# "allow" - Agents can make network requests (required for Claude API)
# "deny"  - No network access (agents will fail to call Claude)
network = "allow"

[resources]
# Resource limits for each agent

# Virtual memory limit
max_memory = "4GB"

# Maximum processes per agent
max_processes = 100

# Maximum open file descriptors
max_open_files = 1024

# Disk quota (future feature)
max_disk = "10GB"

[paths]
# Paths to expose to sandboxed agents

# Read-only tool paths
# These directories are mounted read-only so agents can use tools
read_only = [
    "~/.cargo",           # Rust cargo
    "~/.rustup",          # Rust toolchains
    "~/.nvm",             # Node version manager
    "~/.volta",           # Volta (Node)
    "~/.local/share/mise", # Mise tool versions
    "~/.pyenv",           # Python versions
    "~/.goenv",           # Go versions
    "/usr/local/go",      # System Go
]

# Config files to copy into overlay
# Agents get a copy they can modify without affecting your originals
copy_configs = [
    "~/.gitconfig",       # Git identity (always recommended)
    "~/.npmrc",           # npm registry config
    "~/.cargo/config.toml", # Cargo settings
    "~/.yarnrc",          # Yarn config
    "~/.pip/pip.conf",    # pip config
]

# Cache directories mounted read-write
# WARNING: Agents CAN modify these shared caches
cache_mounts = [
    "~/.npm",             # npm package cache
    "~/.cargo/registry",  # Cargo crate downloads
    "~/.cache/pip",       # pip cache
    "~/.cache/go-build",  # Go build cache
    "~/.local/share/pnpm", # pnpm cache
]

[paths.extra]
# User-defined custom paths

# Additional read-only paths
read_only = [
    # "/opt/custom-tool",
]

# Additional config files to copy
copy_configs = [
    # "~/.custom-tool-rc",
]

[security]
# Security settings

# Paths that are NEVER exposed (in addition to built-in blocklist)
blocked = [
    "~/.ssh",
    "~/.gnupg",
    "~/.aws",
    "~/.azure",
    "~/.config/gcloud",
]
```

## Configuration Sections

### [sandbox]

General sandbox settings.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `enabled` | bool | `true` | Enable bwrap sandboxing |
| `network` | string | `"allow"` | Network policy: `allow` or `deny` |

### [resources]

Resource limits per agent.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `max_memory` | string | `"4GB"` | Virtual memory limit |
| `max_processes` | int | `100` | Process limit |
| `max_open_files` | int | `1024` | File descriptor limit |
| `max_disk` | string | `"10GB"` | Disk quota (future) |

Memory format: `"<number><unit>"` where unit is `KB`, `MB`, or `GB`.

### [paths]

Paths to expose to agents.

| Key | Type | Description |
|-----|------|-------------|
| `read_only` | []string | Directories mounted read-only |
| `copy_configs` | []string | Files copied into overlay |
| `cache_mounts` | []string | Directories mounted read-write |

### [paths.extra]

User-defined additional paths.

| Key | Type | Description |
|-----|------|-------------|
| `read_only` | []string | Additional read-only paths |
| `copy_configs` | []string | Additional config files |

### [security]

Security-related settings.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `blocked` | []string | See below | Paths never exposed |

## Built-in Security Blocklist

These paths are **NEVER** exposed regardless of configuration:

```
~/.ssh              # SSH keys
~/.gnupg            # GPG keys
~/.aws              # AWS credentials
~/.azure            # Azure credentials
~/.config/gcloud    # Google Cloud credentials
~/.kube             # Kubernetes config
~/.docker/config.json # Docker registry auth
~/.netrc            # Generic credentials
~/.password-store   # Pass password manager
~/.local/share/keyrings # GNOME keyring
/etc/shadow         # System passwords
/etc/sudoers        # Sudo configuration
```

---

## Path Expansion

Paths support tilde expansion:

- `~` expands to the user's home directory
- `~/foo` expands to `/home/user/foo`

Relative paths are not supported; use absolute paths or `~`.

## Environment Variables

### Canopy Configuration

| Variable | Description |
|----------|-------------|
| `CANOPY_RESOLVER_TIMEOUT` | Timeout for resolver agents (e.g., `"15m"`, `"1h"`). Overridden by `--resolver-timeout` CLI flag. |

### Passed to Agents

Only these environment variables pass through to agents:

| Pattern | Description |
|---------|-------------|
| `ANTHROPIC_*` | API credentials |
| `PATH` | Executable search path |
| `LANG` | Locale |
| `LC_*` | Locale settings |
| `TERM` | Terminal type |
| `TMPDIR` | Temp directory |
| `TZ` | Timezone |

### System

| Variable | Default | Description |
|----------|---------|-------------|
| `XDG_CACHE_HOME` | `~/.cache` | Cache directory |
| `XDG_RUNTIME_DIR` | `/run/user/$UID` | Runtime directory |
| `TMPDIR` | `/tmp` | Temp directory |

## Persistence Locations

All Canopy state lives in `$XDG_CACHE_HOME/canopy/`:

```
~/.cache/canopy/
├── runs.db           # SQLite database
├── repositories.json # Repository registry
├── daemon.log        # Daemon logs
├── daemon.log.1      # Rotated logs
├── daemon.log.2
└── history/          # JSON run records
    ├── run-abc123.json
    └── run-def456.json
```

### Repository Registry Format

```json
{
    "/absolute/path/to/repo": {
        "id": "uuid-v4",
        "path": "/absolute/path/to/repo",
        "name": "repo-name",
        "created_at": "2024-01-15T10:30:00Z"
    }
}
```

## Best Practices

### Minimal Configuration

Start with defaults and add only what you need:

```toml
[sandbox]
enabled = true
network = "allow"

[paths]
# Add only tools you actually use
read_only = ["~/.nvm"]
copy_configs = ["~/.gitconfig"]
```

### Cache Sharing

Be careful with cache mounts - agents can corrupt shared caches:

```toml
[paths]
# Safe: read-only tool paths
read_only = ["~/.cargo"]

# Risky: writable caches (agents can corrupt)
cache_mounts = ["~/.npm"]
```

### Security Review

Review blocked paths for your workflow:

```toml
[security]
# Block additional sensitive directories
blocked = [
    "~/.ssh",
    "~/.aws",
    "~/private-keys",
    "~/.vault-token",
]
```

## Validation Configuration

The validation configuration file controls post-merge validation and repair agent behavior. Generate it with `canopy init` or create manually.

### Location

```
<project>/.canopy/validation.toml
```

### Full Example

```toml
# Canopy Validation Configuration
# Generated by: canopy init
# Documentation: https://github.com/jzila/canopy/docs/VALIDATION.md

[validation]
# Enable post-merge validation
enabled = true

# Strict mode: revert merge if validation fails (after all repair attempts)
# false = lenient mode: keep merge, file issue for manual fix
strict = false

# Global timeout for all validation steps
timeout = "5m"

# Maximum repair agent attempts before filing issue
max_repair_attempts = 3

[[validation.steps]]
name = "typecheck"
command = "npm run type-check"
timeout = "2m"
required = true

[[validation.steps]]
name = "lint"
command = "npm run lint"
timeout = "3m"
required = true

[[validation.steps]]
name = "test"
command = "npm test"
timeout = "5m"
required = true

[[validation.steps]]
name = "build"
command = "npm run build"
timeout = "5m"
required = false
```

### [validation]

General validation settings.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `enabled` | bool | `false` | Enable post-merge validation |
| `strict` | bool | `false` | Revert merge on validation failure (after repair attempts) |
| `timeout` | string | `"5m"` | Global timeout for all steps |
| `max_repair_attempts` | int | `3` | Maximum repair agent retries before filing issue |

#### Strict vs Lenient Mode

- **Strict mode** (`strict = true`): If validation fails after all repair attempts, the merge is reverted. Use this when you cannot tolerate broken code in main.

- **Lenient mode** (`strict = false`, default): If validation fails after all repair attempts, the merge remains but a high-priority bead is filed for manual intervention. Use this when you prefer to keep progress and fix forward.

### [[validation.steps]]

Each validation step to run after merge.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `name` | string | required | Human-readable step name (used in logs/issues) |
| `command` | string | required | Shell command to execute |
| `timeout` | string | global | Step-specific timeout (overrides `[validation].timeout`) |
| `required` | bool | `false` | Stop validation if this step fails |

#### Step Execution

Steps run sequentially in the order defined. Execution stops when:
- A **required** step fails
- Any step fails in **strict** mode
- All steps complete

#### Timeout Format

Duration format: Go duration string (e.g., `"2m"`, `"5m"`, `"1h"`, `"30s"`)

### Validation Status Values

| Status | Description |
|--------|-------------|
| `pending` | Validation not yet started |
| `running` | Validation steps executing |
| `passed` | All steps succeeded |
| `failed` | Required step failed or strict mode failure |
| `skipped` | Validation disabled |
| `repairing` | Repair agent attempting to fix failure |
